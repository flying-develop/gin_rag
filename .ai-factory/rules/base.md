# Базовые правила проекта

> Стартовые конвенции на основе стека (Go 1.23+, Gin, GORM +
> golang-migrate, langchaingo). Правь по мере появления кода.

## Соглашения об именовании

- Пакеты: короткие, строчные, без подчёркиваний (`dialog`, `httpserver`)
- Файлы: `snake_case.go` (`dialog_service.go`, `dialog_handler.go`)
- Экспортируемые идентификаторы: `PascalCase`; неэкспортируемые: `camelCase`
- Конструкторы: `NewXxx(...)`
- Интерфейсы: по роли, часто с суффиксом `-er` (`Classifier`,
  `DialogRepository`); объявляются на стороне потребителя
- DTO: суффиксы `Request`/`Response` (`SendMessageRequest`)
- Сентинел-ошибки: `ErrXxx` (`ErrDialogNotFound`)

## Структура модулей

Архитектура — Structured Modules (Technical Layer), подробности в
`.ai-factory/ARCHITECTURE.md`. Каждый домен — модуль в
`internal/modules/<module>/`:

- `handler/` — Gin-хендлеры: только биндинг/валидация входа, вызов
  сервиса, формирование ответа; без бизнес-логики и без прямых
  обращений к БД
- `service/` — бизнес-логика модуля, включая langchaingo-цепочки и
  state machine
- `repository/` — единственная точка доступа к БД модуля через GORM;
  вызовы `*gorm.DB` вне этого слоя запрещены; бизнес-логики в
  репозитории нет
- `model/` — GORM-модели модуля
- `dto/` — структуры запросов/ответов модуля
- `internal/infrastructure/` — сквозная инфраструктура: конфиг,
  инициализация БД/Redis/Qdrant/LLM, HTTP-сервер, логирование,
  обработка ошибок; без бизнес-логики и специфики отдельного модуля

Межмодульное взаимодействие — только через публичный интерфейс сервиса
другого модуля, не через его репозитории или модели напрямую.

## Работа с БД

- Доступ к БД — только через репозитории. `db.First()`, `db.Where()`,
  raw SQL вне слоя `repository/` запрещены.
- Транзакции инициируются в сервисе (`db.Transaction(...)` / хелпер из
  `internal/infrastructure/db`), операции внутри — через репозитории.
- Каждый метод репозитория/сервиса принимает `context.Context` первым
  аргументом; в GORM — `db.WithContext(ctx)`.
- Схема меняется только миграциями golang-migrate (up + down файл),
  не через `AutoMigrate` в проде.

## Обработка ошибок

- Оборачивать ошибки с контекстом: `fmt.Errorf("load dialog %d: %w", id, err)`
- Доменные ошибки — сентинел-переменные (`ErrDialogNotFound`) или
  типизированные ошибки с кодом, а не «голый» `errors.New` без контекста
- На границе API — единый обработчик (Gin middleware) превращает
  доменные ошибки в структурированный JSON (`application/problem+json`)
- `panic` в прикладном коде запрещён; recovery-middleware — только как
  последний рубеж

## Контроль потока выполнения

- Плоский, читаемый control flow: guard clauses, ранние `return`,
  небольшие именованные хелперы. Граничные случаи — в начале функции,
  основной путь — на виду. Не игнорировать возвращаемые ошибки.

## Логирование

- Структурированное логирование через `log/slog`; уровень — через
  `LOG_LEVEL`. Логгер передаётся в сервисы явно (или через контекст),
  не глобальный `log.Println`. `fmt.Println` в прикладном коде не
  использовать.

## Инструменты и проверки

- Форматирование: `gofmt` / `goimports` (обязательно перед сдачей)
- Статанализ: `go vet`, `golangci-lint run`
- Сборка: `go build ./...`
- Тесты: `go test ./...`; для новых методов сервисов и репозиториев —
  тесты. БД-тесты — против реального Postgres из docker-compose, без
  моков.
- Doc-комментарии экспортируемых типов и пояснения к коду — на русском
  языке.

## Окружение

- Локальное окружение (БД, Redis, Qdrant, сам сервис) поднимается через
  Docker / docker compose, а не напрямую на хосте.
- Составные shell-команды разбивать на отдельные шаги, не склеивать
  через `&&`.
- Проект без git — ветки не создаются, изменения вносятся напрямую в
  рабочую директорию, чекпоинты в планах — только логические.
